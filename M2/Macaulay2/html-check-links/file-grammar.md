# `grammar.y`, `grammar.h` — Bison grammar for HTML scanning

`grammar.y` is the **Bison grammar** for parsing HTML. The
grammar is deliberately *loose* — HTML in the wild violates
strict spec in countless ways, and the link-checker only cares
about `href`/`src` attributes anyway.

Part of [`html-check-links/`](README.md).


The grammar uses the **buffer macro** from
[`file-buffer.md`](file-buffer.md) (`BUFFER(location)`) to build
a dynamically-sized stack of `location` structs — used to track
open tags for matching against close tags.

## What the grammar parses

Roughly:

```
document : tag*
tag      : open_tag content close_tag
         | self_closing_tag
         | text
open_tag : '<' name attrs '>'
attrs    : (name '=' value)*
```

Where `attrs` with `name = "href"` or `name = "src"` get **collected**
into a list checked later.

The grammar is **error-tolerant**: malformed tags don't abort
parsing; they just don't yield href/src values.

## `grammar.h`

The header (auto-generated by Bison plus a small hand-written
section) declares the token IDs and tag-tracking helpers. The
grammar uses ~15 token kinds: `LT`, `GT`, `SLASH`, `EQ`, `STRING`,
`NAME`, etc. Each is recognised by [`file-lex.md`](file-lex.md).

## Tag-balancing

The `openings` buffer tracks open tags. When a close tag arrives:

```
top_of_openings.opener == close_tag_name ?
   pop (matched)
   else report mismatch (e.g. </div> with no <div>)
```

The mismatch is informational — the link checker doesn't *fail*
on tag-balancing errors (real-world HTML often has them), but it
warns.

## Why not use a real HTML parser?

The classic options:

- **libxml2's HTMLParser** — heavy dependency, complex API.
- **Browsers' parsers** — way overkill.
- **regex-based scraping** — fragile.

A 200-line Bison grammar is enough for "get hrefs out of HTML"
and adds no library dependencies beyond flex/bison.
